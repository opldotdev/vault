@opl.dev/vault

A generic Bitcoin key vault. One encrypted document holds every key a person or agent has. Hardware or a passphrase seals it. It derives and signs, so a private key never leaves it in the clear unless someone explicitly asks it to.

Repository opldotdev/vault, npm @opl.dev/vault. Reader: the person deciding the package's shape, then the agents building it. This plan looks at the vault on its own. It does not name who will use it, on purpose. Nothing here is built.

What a vault is for

Every Bitcoin tool eventually writes the same three hundred lines: find the key file, ask for a password, decrypt, hand a WIF to the code that needs it, hope nobody logs it. The vault exists so that never gets written again. It has one job with four parts.

  • Hold secrets of every shape a Bitcoin user has: raw entropy, mnemonics, extended keys, single WIFs, detached account keys, key shares, and symmetric encryption keys.
  • Seal them under whatever the machine offers, from a hardware enclave with a fingerprint down to a passphrase in an environment variable, with the same file either way.
  • Use them without releasing them: derive public keys, derive child keys into new entries, sign, and encrypt or decrypt, all inside the vault.
  • Move them safely: import anything, encrypted or not, and export only in encrypted form, to a passphrase or to another vault's public key.

First principles

  • Nothing leaves in the clear by default. The vault's normal outputs are public keys, signatures, ciphertext, and new sealed entries. Revealing a private key is a separate, named, logged operation that demands a fresh unlock and a reason.
  • Entropy is the master. Per BRC-157 the fundamental secret is 32 bytes of entropy. The mnemonic and BRC-140 backup shares are two encodings of it. The root key is derived, its public key is the BRC-100 identity key, and every operational key is a BRC-42 derivation from a root. The vault knows this so callers do not have to.
  • Roles are derivations. A key is not "the payment key" because someone flagged it. It is the payment key because it was derived for that purpose from a root the vault holds. Flags survive only for legacy standalone keys that were imported as-is.
  • One document, many wraps. The document is encrypted under one random vault key. That vault key can be wrapped more than once, by an enclave and by a recovery passphrase, so losing the machine does not lose the vault. This is the key-slot idea from disk encryption.
  • Secrets never appear on a command line. Passphrases come from a file, from standard input, or from a named environment variable read verbatim. An empty variable is an error, never a fallback.
  • Agents are first-class callers. Every command has a JSON mode, stable exit codes, and a non-interactive path. Every unlock carries a reason string, so a human reviewing the log can see what wanted the key and why.
  • Stand on the published formats. The envelope is bitcoin-backup's, extended, not replaced. Derivation follows the BRCs. Import accepts every payload type bitcoin-backup already knows.

The document

  vault.bep                                     (one file, mode 0600, atomic writes, lock file)
  ├ header        version · document id · created · key slots[]
  │                 slot: { kind: enclave | device-p256 | passphrase, wrapped vault key, public key or kdf params }
  └ ciphertext    AES-256-GCM under the vault key, over:
      ├ entries[]
      │   id · kind · label · tags[] · created · updated
      │   kind ∈ entropy | mnemonic | hd-private | hd-public | private | wif | account | share | symmetric
      │   value (the secret, or the public part for public kinds)
      │   derivation?  { scheme: brc157 | bip32 | brc42 | type42 | legacy-*, path, parent id, index, cohort }
      │   roles?       legacy flags only: identity · funding · ordinals · encryption
      │   shares?      { threshold, total, share ids[] }
      │   metadata     free-form string map, never used for derivation
      └ log[]         time · operation · entry id · reason · caller · outcome   (no secret material)

The plaintext document is a schema-versioned JSON object with a published JSON Schema. Unknown versions, unknown kinds, and unknown slot types fail closed. The value of an entry is the only field that ever holds a secret. Everything else may be listed while the vault is locked.

The API

The library is isomorphic: WebCrypto for everything, with storage and sealing behind two small interfaces. Node, Bun, and the browser share the core.

Sealing providers

ProviderWhereHow the vault key is wrapped
Secure EnclavemacOS on Apple siliconECIES to an enclave P-256 key agreement key; Touch ID to unwrap. Lifted from an existing Swift helper that already does exactly this.
Passkey PRFBrowsers with a platform authenticatorHKDF of the PRF output wraps the vault key; Face ID or Touch ID to unwrap. Non-exportable by design, so a passphrase slot is required alongside it.

PassphraseAnywhere, headless, CIPBKDF2-SHA256 at bitcoin-backup's recommended iterations. The recovery slot every vault should have.

Slots make these composable. A laptop vault typically has an enclave slot and a passphrase slot. A server vault has a device-key slot whose passphrase lives in the host's secret manager. A browser vault has a PRF slot and a passphrase slot. The file is the same.

The CLI

Binary name bsv-vault, because vault is already a well-known secrets tool on many machines. Installed with the library or run with bunx. Every command takes --json, --vault <path>, and --reason. Passphrases only via --passphrase-file, --passphrase-stdin, or a named env var.

  bsv-vault init [--slot enclave|passphrase|device]      create a vault, add a first slot
  bsv-vault slot add|remove|list                         manage wraps of the vault key
  bsv-vault list [--kind] [--tag] [--role]               inventory, works locked
  bsv-vault import <file|-> [--passphrase-…]              any bitcoin-backup payload, plain or encrypted, or a foreign vault
  bsv-vault generate entropy|key|symmetric [--label]      new secrets, mnemonic shown once on request
  bsv-vault derive <id> --scheme brc157 --index 1         a profile root as a new entry
  bsv-vault derive <id> --scheme brc42 --protocol … --key-id …
  bsv-vault pubkey <id> [derivation]                      public key without unlocking the entry's role
  bsv-vault sign <id> [derivation] <data|->              signature out, key stays in
  bsv-vault shares split <id> -t 2 -n 3 | recover …       BRC-140 over entropy
  bsv-vault export <id> --to-passphrase | --to-pubkey <hex>
  bsv-vault backup [--to-passphrase-…]                    whole vault as a portable .bep
  bsv-vault reveal <id> --reason "…"                      the one plaintext path, logged
  bsv-vault log [--since]                                 what touched what, and why
  bsv-vault doctor                                        provider availability, file permissions, slot health

This supersedes the bbackup command line. Encrypting, decrypting, and upgrading a loose .bep are covered by import, export, and backup, with the difference that secrets never touch argv. bitcoin-backup stays the envelope library and keeps its CLI as a thin compatibility shim that points here.

Ideas worth having in the foundation

  • Seal to a public key. exportSealed to any vault's public key is the primitive for moving a key between two machines with no shared secret: one vault publishes its slot public key, the other seals to it. It falls out of the ECIES layout for free.
  • Unlock sessions with a TTL and a reason. A signer handle expires. The reason is what an audit log shows and what a consent prompt can display.
  • Locked inventory. Listing labels, kinds, tags, and public keys without unlocking means tools can show what exists before asking for a fingerprint.
  • Derivation cohorts. A mnemonic from before the BRC-157 convention may have used an unhardened path. The descriptor records which, so a vault never silently re-derives an old identity under a new rule.
  • Foreign vault import. Accept another vault document, given its credentials, as a batch import. This is how migration from every existing key store happens in one command.
  • Doctor. One command that says whether the enclave is available, whether the file mode is right, whether every slot still unwraps, and whether a recovery slot exists.
  • Test vectors as fixtures. The BRC-157 worked example, BRC-42 vectors, and every bitcoin-backup fixture live in the repo, so conformance is a test, not a claim.
  • Zeroing. Secret buffers are zeroed after use where the runtime allows, and the API never returns a secret as a string it did not have to.
  • File lock and atomic writes. Two processes on one vault do not corrupt it. Writes go to a temp file and rename.

Security notes

A root never signs. An entropy entry only derives. A profile root derives and issues certificates. Only derived keys sign transactions. This is BRC-100's everyday-versus-privileged separation made mechanical.

Reveal is the attack surface. It exists for migration and for tools that have not adopted signers. It requires a fresh unlock, a reason, and writes a log line. A vault can be created with reveal disabled, and that setting is inside the ciphertext so it cannot be flipped from outside.

Passphrase strength is enforced at creation. The envelope resists brute force only as well as the passphrase does. A passphrase slot below the minimum is refused, and the CLI can generate one.

PRF ciphertext dies with the passkey. A PRF slot is never the only slot. Creating one without a passphrase slot is refused.

Sealed export is not custody transfer. Sealing an entry to another vault's public key duplicates authority. The log records it, and the CLI says so in plain words before doing it.

The steps

1. Envelope extension in bitcoin-backup

bitcoin-backup · small · first · depends on decision 2

Add key slots to the envelope header and the device-p256 wrapping scheme using the enclave helper's exact ECIES layout. Add the mnemonic derivation descriptor. Existing single-passphrase files remain valid and decrypt unchanged. Unknown versions and schemes fail closed.

Done when: round-trip tests pass for passphrase, device-key, and multi-slot files, every legacy fixture still decrypts, and re-wrapping between slots preserves the payload byte for byte.

2. Core library

opldotdev/vault · medium · depends on step 1 and decisions 1, 3, 4

The document schema and its JSON Schema, the entry kinds and derivation descriptors, the sealing provider and storage interfaces, lifecycle and inventory, import of every bitcoin-backup payload and of a foreign vault document, generate, derive per BRC-157, BIP-32, and BRC-42, the session-bound signer, encrypt and decrypt, BRC-140 shares, encrypted and sealed export, reveal with logging, and the audit log. WebCrypto throughout. Zeroing where possible.

Done when: the published BRC-157 worked example reproduces its root and identity key, BRC-42 vectors pass, every bitcoin-backup fixture imports, a signer cannot be coerced into yielding its key in tests, and the package has no runtime dependency beyond the Bitcoin SDK and bitcoin-backup.

3. Providers and storage

opldotdev/vault · medium · parallel with step 2

Secure Enclave provider from the existing Swift helper, moved into this repository with its build script. Passphrase provider. Device-key provider. File storage with lock file, atomic writes, and mode 0600. If decision 4 says so: PRF provider and IndexedDB storage for the browser.

Done when: the same vault file opens on a Mac with Touch ID and on Linux with a passphrase, adding and removing slots works in both directions, and the browser build opens a document created by the CLI.

4. CLI

opldotdev/vault · medium · depends on steps 2 and 3

Every command in the list above, with --json, stable exit codes, no secrets on argv, and a non-interactive path for each. A doctor command. Shell completions. A compatibility note for people arriving from bbackup.

Done when: a fresh machine goes from nothing to a sealed vault with a derived signing key and a printed share set using only the CLI, an agent can do the same with --json and no TTY, and no command accepts a secret as an argument.

Publish @opl.dev/vault and the bitcoin-backup release. Deprecate the bbackup command line with a pointer. Write the README as the spec: document schema, provider contract, CLI reference, and the security notes above. Hand back the package name, version, and the schema URL.

Questions answered

Should it be just an import package?

No. A library alone means every tool writes its own command line, and the command line is where secrets get pasted into argv. The library and the CLI ship together, and the CLI is the reference caller of the library.

Should it use bitcoin-backup?

Yes, as the envelope, extended with slots and a device-key scheme. Inventing a second envelope would split the ecosystem's backup format in two. The vault also imports every payload type bitcoin-backup knows, which is how existing key files migrate in one command.

Should it deliver derived keys?

It delivers derived entries and derived public keys, and it signs with derived keys. It does not hand out derived private keys any more than root ones. A caller that truly needs the bytes uses reveal, with a reason, and the log shows it.

Does the CLI replace bbackup?

For people, yes. Every bbackup operation exists here without a passphrase on the command line. bitcoin-backup keeps its command as a shim so old scripts print a pointer instead of breaking.

Can one entry be identity, funding, and ordinals at once?

One entropy entry can be the source of all three, through derivation. One raw key flagged as all three is a legacy standalone entry and is never created new.
